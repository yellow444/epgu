# Внешний адрес информационной системы

В техпортале у информационной системы два адреса, и оба должны вести на наш
приёмник:

| Поле в техпортале | Что вписать |
| --- | --- |
| URL системы | `https://<домен>/is` |
| URL для отправки push сообщений | `https://<домен>/push` |

Приёмник слушает порт 58080 и отдаёт обычный HTTP. TLS и домен живут на
внешнем хосте: у стенда белого адреса нет, а техпортал принимает только
`https` и обычный доверенный сертификат.

## Схема

```
ЕПГУ -> https://smev.example.ru/is и /push   (443, сертификат Let's Encrypt)
        VPS, nginx
        туннель VPS -> машина со стендом
        порт 58080, сервис inbound
        порт 55000, операторский API  никогда наружу
```

Наружу открыт ровно один порт и ровно два пути. Всё остальное на VPS
отвечает 404, а операторские методы стенда физически недоступны из интернета:
они слушают только localhost.

## Что сделать на VPS

1. A-запись домена на адрес VPS. Одна запись, ничего больше:

   | Поле | Значение |
   | --- | --- |
   | Имя | `smev` (получится `smev.mirasnowfox.ru`) |
   | Тип | `A` |
   | Значение | адрес VPS |
   | TTL | оставить по умолчанию |

   Зона `mirasnowfox.ru` живёт на `ns1.hosting.reg.ru` и `ns2.hosting.reg.ru`,
   значит запись правится в панели reg.ru, раздел управления DNS-зоной домена.
   Существующие записи трогать не нужно: сам домен смотрит на хостинг
   `37.140.192.190`, а MX ведут на `mx1.hosting.reg.ru` и `mx2.hosting.reg.ru`,
   то есть на тот же ящик `smev@mirasnowfox.ru`, из которого стенд читает
   переписку с поддержкой. Поддомен от этого не зависит и почту не затронет.

   Если у VPS только IPv6, вместо `A` заводится `AAAA` с тем же именем.

   Проверить, что запись разошлась:

   ```bash
   nslookup smev.mirasnowfox.ru
   ```

   Сертификат выпускается только после того, как имя начало разрешаться:
   certbot проверяет домен снаружи.
2. Канал до машины со стендом. Пробрасывать порт домашнего роутера не нужно и
   не стоит: адрес меняется, а порт остаётся открытым всему интернету.
   Достаточно постоянного туннеля, поднятого со стороны стенда:

   ```bash
   # на машине со стендом, ключ уже разложен
   autossh -M 0 -N -R 127.0.0.1:58080:127.0.0.1:58080 vpsuser@smev.example.ru
   ```

   Тогда на VPS порт 58080 доступен только на localhost, и наружу его отдаёт
   один nginx. Альтернатива - WireGuard между VPS и стендом, тогда в
   `proxy_pass` идёт адрес стенда в туннельной сети.
3. Сертификат: `certbot --nginx -d smev.example.ru`.
4. Конфиг nginx: [`nginx-smev.conf`](nginx-smev.conf), в нём подставьте домен
   и, если используете WireGuard, адрес стенда.
5. Проверка снаружи:

   ```bash
   curl -s https://smev.example.ru/is
   curl -s https://smev.example.ru/push
   ```

   Первый ответ содержит `endpoints`, второй - `code: OK`. Если пришло что-то
   другое, значит запрос до стенда не дошёл.

## Что сделать на стенде

В `.env` рядом с `docker-compose.yml`:

```dotenv
INBOUND_PUBLIC_URL=https://smev.example.ru
INBOUND_TRUSTED_PROXIES=127.0.0.1/32
```

`INBOUND_TRUSTED_PROXIES` обязателен: без него отправителем каждого запроса
будет виден прокси, а не ЕПГУ. Если туннель WireGuard, укажите его сеть.

Кнопка «Проверить адрес снаружи» на вкладке «Входящие» гоняет запрос через
интернет и говорит, вернулся ли он на наш приёмник.

## Про защиту приёмника

`INBOUND_TOKEN` для этого адреса не годится: ЕПГУ про наш секрет не знает и
заголовок не пришлёт, а приёмник ответит 401. Список сетей
`INBOUND_ALLOW_NETS` тоже нельзя заполнить заранее: опубликованных адресов, с
которых ходит ЕПГУ, в документации нет.

Поэтому порядок такой: сначала адрес открыт, работают ограничение частоты и
журнал. После первого настоящего запроса в журнале виден адрес отправителя,
и вот тогда сеть прописывается в `INBOUND_ALLOW_NETS`, а порт закрывается для
всех остальных. Подробности в
[`docs/context/11-inbound-endpoint.md`](../../docs/context/11-inbound-endpoint.md).
