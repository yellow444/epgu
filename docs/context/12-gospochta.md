# 12 - Госпочта организации: официальный API ГЭПС

## Короткий вывод

Госпочту (ГЭПС) в личном кабинете организации можно читать **по официальному
API ЕПГУ**, через тот же маркер доступа и тот же ГОСТ TLS хост, которыми мы уже
пользуемся. Браузерный робот с Selenium для этого не нужен.

Документ лежит у нас в снимке каталога:
`docs/api_for_gu/source/Specifikaciya_API_GEPS_v1.0.docx`, «Спецификация API
ГЭПС. Приложение "Получение уведомлений Госпочты и Новости"», версия 1.0 от
29.01.2026. В каталоге это `protocol-specification`, SHA-256 записан в
[`catalog.json`](../api_for_gu/catalog.json).

## Четыре метода ГЭПС

Все идут через прокси API ЕПГУ, то есть с маркером доступа организации.
Хост тестовой среды из примеров спецификации: `svcdev-gostapi.test.gosuslugi.ru`.

| Шаг | Метод |
| --- | --- |
| 1. Заказать список | `POST /api/gusmev/proxy/geps-api-ext/api/messages/v1/search` |
| 2. Забрать список | `GET /api/gusmev/proxy/geps-api-ext/api/messages/v1/search/{searchTaskUuid}` |
| 3. Карточка уведомления | `GET .../api/messages/v1/message/{threadUuid}/{messageUuid}` |
| 4. Вложение или подпись | `GET .../api/messages/v1/attachment/{messageUuid}/{attachmentUuid}/{file\|sig}` |

Заказ списка: `startDateTime`, `endDateTime`, `statusFilter` (`ANY`, `READ`,
`UNREAD`). В ответ `searchTaskUuid`.

Список: `searchTaskStatus` (`SEARCH`, `PROCESSING`, `COMPLETED`, `ERROR`) и
`messageList` с полями `threadUuid`, `messageUuid`, `feedTitle` (отправитель),
`feedSubtitle` (тема), `isRead`, `createDate`.

Вложения в карточке: `attachmentUuid`, `fileName`, `fileSize`, `mimeType`,
`signed` (есть ли отсоединённая подпись), `statusMnemonic` и описание статуса.

## Ограничения, которые определяют архитектуру

- Диапазон поиска не больше **суток**, глубина не больше **30 дней**.
- **5 запросов на формирование списка в день** и **15 запросов на получение
  готового списка в день**. Карточки и вложения без лимита по количеству
  (78 и 155 запросов в секунду).
- Список готовится асинхронно, забирать рекомендуется **через час**, живёт
  **7 дней**.
- Нужна роль **«Руководитель организации» или «Администратор»**, иначе 403.
- Вызов равнозначен входу на портал: по ряду НПА уведомление считается
  врученным с момента входа. Постановление Правительства № 606 от 29.06.2016
  (извещения ФССП) и № 947 от 19.06.2021 (постановления по административным
  делам) прямо на это опираются. То есть **читать почту нельзя «на всякий
  случай»**: чтение запускает сроки.

Из лимитов следует режим работы: один заказ списка в сутки на сутки, забор
результата через час, дальше карточки и вложения без ограничений. Никакого
опроса каждые пять минут.

## Браузерный сбор

До появления API ГЭПС уведомления забирали через браузер: Selenium, вход по
ЭЦП, листание ленты, печать страниц в PDF. Этот путь остаётся запасным для
того, чего в API нет, и для организаций без доступа к API ЕПГУ.

Здесь его нет намеренно. Эта часть развивается отдельно, в приватной поставке
рядом с репозиторием. В публичный репозиторий из неё ничего не переносим.

Что из того опыта пригодилось здесь:

- Формат результата `Letters/Letter` (дата, отправитель, тема, текст,
  ссылка, тип документа, список файлов). Под него уже пишут интеграции,
  поэтому наш ответ по ГЭПС имеет смысл уметь отдавать и в таком виде.
- Модель работы: заявка с идентификатором, асинхронный воркер, результат
  файлом плюс папка вложений. Она хорошо ложится на лимиты ГЭПС.

## Роли: кем может быть обычное ООО

В регламенте подключения к API Госуслуг ролей ровно две, и «поставщика» среди
них нет:

- **Организация-вендор** - разработчик информационной системы.
- **Организация-потребитель** - организация, выполняющая запрос к API,
  используя ИС. Там же прямо сказано: вендор и потребитель могут быть одним и
  тем же лицом.

Обычное ООО без властных полномочий - это **вендор и потребитель
одновременно**: сами написали ИС, сами ею пользуемся. В заявке на доступ есть
параметр «Владелец ИС является организацией-потребителем» со значением «Да».
Если планируется работать в продуктивной среде для сторонних потребителей,
регистрируется ещё и тестовая организация-потребитель.

Слово «поставщик» относится к другой системе - к СМЭВ, где поставщик сведений
это ведомство или организация, за которой сведения закреплены нормативным
актом. Стать поставщиком по своему желанию нельзя, для этого нужны полномочия
или закреплённая за организацией функция. Поэтому наш реалистичный статус -
потребитель, а услуги мы подаём от лица своей организации либо от лица
пользователя с его согласия.

## Приставы: что реально доступно

В снимке каталога уже есть четыре услуги ФССП, все в статусе `reference`:

| Код | Услуга |
| --- | --- |
| `60010153` | Предоставление информации о наличии исполнительного производства онлайн |
| `10000000352` | Предоставление информации о ходе исполнительного производства онлайн |
| `10000000367` | Подача заявлений, ходатайств, объяснений, отводов и жалоб по исполнительному производству |
| `10000000396` | Информация об исполнительных производствах для снятия ограничений на выезд |

Спецификации на них лежат локально в `docs/api_for_gu/source/`. Для
`60010153` в проекте уже есть `req.xml` и тесты транспорта, статус держится
`reference` до тех пор, пока форма заявителя не научится отбивать
демонстрационные данные.

Вторая половина работы с приставами - входящая: извещения ФССП приходят именно
в Госпочту, и по постановлению № 606 они считаются доставленными с момента
входа на портал. То есть чтение ГЭПС и подача по `10000000367` вместе дают
замкнутый цикл: увидели извещение, ответили ходатайством или жалобой.

## Что уже сделано

Клиент ГЭПС в библиотеке: [`python-epgu/src/epgu/geps.py`](../../python-epgu/src/epgu/geps.py)
и четыре метода в [`EpguClient`](../../python-epgu/src/epgu/client.py) -
`geps_search`, `geps_search_result`, `geps_message`, `geps_attachment`.
Модуль лежит на верхнем уровне пакета, а не в `services/`: `services/__init__`
тянет `submit`, тот тянет клиент, и получался круговой импорт.

В библиотеке живут проверки, которые дешевле сделать у себя:

- период не больше суток, глубина не больше 30 дней, конец не в будущем,
  даты обязательно со смещением часового пояса;
- `searchTaskUuid`, `threadUuid`, `messageUuid` и `attachmentUuid` проверяются
  как UUID до обращения к сети;
- имя файла из `Content-Disposition` чистится до простого имени: оно приходит
  от отправителя, а файл потом ложится на диск;
- непонятная дата в ответе не роняет весь список.

Четыре метода бэкенда поверх существующего маркера доступа:

| Метод | Что делает |
| --- | --- |
| `POST /geps/search` | заказ списка за период, возвращает `searchTaskUuid` и остаток попыток |
| `GET /geps/search/{task}` | готовый список постранично; пока не готов, отдаёт `status` без выдумывания пустого результата |
| `GET /geps/message/{thread}/{message}` | карточка: текст, вложения, история статусов |
| `GET /geps/attachment/{message}/{attachment}/{file\|sig}` | файл или отсоединённая подпись, потоком, с ограничением размера |

Плюс `GET /geps/quota`: остаток суточных попыток, читается без обращения к ЕПГУ.

Учёт лимитов - [`geps_quota.py`](../../api-gosuslugi-backend/geps_quota.py).
Счётчик на томе, сутки по московскому времени. Попытка занимается **до**
обращения к ЕПГУ: сетевой сбой на той стороне тоже её расходует, и считать
только удачные было бы враньём. Когда попытки кончились, бэкенд отвечает 429
сам, не тратя обращение.

Отдельно разобраны ответы ГЭПС, у которых есть свой смысл: 403 говорит про
роль руководителя или администратора, 404 про то, что результат старше семи
дней, 429 про лимит на стороне ЕПГУ.

## Хранение и планировщик

[`geps_store.py`](../../api-gosuslugi-backend/geps_store.py) держит на томе всё,
что удалось получить: результат ГЭПС живёт семь дней и потом пропадает, а
перезаказать его стоит одной из пяти суточных попыток.

```
jobs.json                     заявки на список и их состояние
messages.json                 уведомления: краткие данные и карточки
files/<messageUuid>/<файл>    вложения и отсоединённые подписи
```

Заявка проходит состояния `ordered`, `ready`, `failed`, `expired`. Один и тот
же период дважды не заказывается. Имя файла чистится ещё раз уже здесь: оно
приходит от отправителя и попадает в путь на диске.

[`geps_scheduler.py`](../../api-gosuslugi-backend/geps_scheduler.py) - фоновая
задача. Такт делает три вещи: забирает результат по заявкам, которым подошло
время, заказывает список за предыдущие сутки, если его ещё не заказывали, и
добирает карточки уведомлений, у которых их нет. Первая проверка результата
через час после заказа, дальше раз в час. Заявка старше семи дней помечается
как протухшая, и за ней уже не ходят.

Такт ничего не знает про сеть: все обращения идут через шлюз, который передают
снаружи. Поэтому он проверяется целиком, без ЕПГУ.

**Автоматический режим по умолчанию выключен, и это не перестраховка.**
Обращение к ГЭПС равнозначно входу на портал: уведомление считается вручённым
с этого момента, и с него же идут процессуальные сроки. Фоновая задача, которая
молча забирает почту, начинает эти сроки без ведома человека. Поэтому включение
- отдельное действие оператора, и оно пишется в лог.

Второе ограничение честное и никуда не денется: своего маркера доступа у
фоновой задачи нет и быть не может, API-Key вводит человек. Пока сессия
оператора жива, планировщик работает; когда её нет, такт пропускается с
причиной «нет действующего маркера доступа», и это видно в состоянии.

## Вкладка «Госпочта»

[`Gospochta.js`](../../api-gosuslugi-client/src/components/Gospochta/Gospochta.js).
Открывается и читается с диска стенда, в ЕПГУ при этом не ходит: показывать уже
полученное можно сколько угодно, а вот обращение к ГЭПС стоит суточной попытки.

Что на вкладке:

- предупреждение о сроках, которое не закрывается;
- переключатель автоматического забора и кнопка «Забрать сейчас», которая
  сначала спрашивает подтверждение и объясняет последствия;
- остаток суточных попыток по обоим сервисам, состояние планировщика, причина
  пропуска последнего такта;
- заказанные списки с их состоянием;
- уведомления по 10 на страницу с фильтром «только непрочитанные»;
- карточка в боковой панели: текст, вложения с кнопками сохранения и
  отсоединённой подписи, история статусов.

Текст уведомления приходит из ЕПГУ готовой разметкой со стилями. Вставлять
чужой HTML в свою страницу нельзя, поэтому он показывается в `iframe` с пустым
`sandbox`: ни скриптов, ни доступа к странице.

## Отдача внешним системам

[`outbound.py`](../../api-gosuslugi-backend/outbound.py), отдельный процесс и
отдельный порт 58081, как у приёмника. Причина та же: наружу смотрит только он.

Два правила, которые определяют этот процесс:

- **Он никогда не ходит в ЕПГУ.** Отдаётся только то, что уже лежит на томе.
  Иначе чужая информационная система своим запросом запускала бы нам
  процессуальные сроки. Вложение, которое оператор ещё не скачал, отдаётся
  как 409 «файл ещё не скачан», а не подтягивается из ЕПГУ.
- **Он закрыт по умолчанию.** Приёмник обязан принимать всё подряд, здесь
  наоборот: пока не задан `OUTBOUND_TOKEN` или `OUTBOUND_ALLOW_NETS`, на
  данные приходит 503 с объяснением, отвечает только `/health`. Проверки
  отправителя те же, что у приёмника, только со своими переменными.

| Путь | Что отдаёт |
| --- | --- |
| `/messages` | список в нашем JSON, есть `since` для инкрементальной выгрузки |
| `/messages/{uuid}` | карточка: текст без разметки, исходный HTML, статусы |
| `/messages/{uuid}/attachments/{uuid}` | файл или подпись, если уже скачаны |
| `/letters` | то же самое в формате `Letters/Letter` |

Формат `Letters/Letter` взят из давно живущей интеграции с 1С, чтобы её не
переписывать. Соответствие полей описано в коде; `Text` идёт без разметки,
`Ref` содержит `messageUuid`, `BodyJSON` - полную запись, если нужны детали.
Порядок элементов зафиксирован тестом: чужая интеграция читает документ
последовательно.

Пути к файлам на нашем диске наружу не отдаются, а файл выдаётся только если
он лежит внутри каталога хранилища: запись могли подправить руками.

## Попытка живого прогона 17.08.2026

Прогон на настоящем доступе не состоялся, и упирается это не в код.

Цепочка доходит до ЕСИА и обрывается там же:

```
POST /api/accessTkn_esia
app: Запрос маркера ЕСИА: https://esia-portal1.test.gosuslugi.ru/esia-rs/api/public/v1/orgs/ext-app/<api-key>/tkn
app: ESIA token request failed with HTTP 404
```

404 на этом адресе означает, что API-Key в нём не найден. Так и есть: в `.env`
на стенде `apikey` длиной четыре символа, то есть заглушка, а не GUID из
техпортала. В хранилище сертификатов при этом лежит только самоподписанный
`biokey`, которым мы проверяли саму подпись.

Чтобы прогон состоялся, нужно три вещи, и все три вне репозитория:

1. **API-Key организации** из техпортала ЕСИА, выпущенный по заявке.
2. **Сертификат организации** с закрытым ключом в хранилище контейнера.
   Самоподписанный для ЕСИА не годится.
3. **Роль руководителя организации или администратора** на ЕПГУ, иначе ГЭПС
   ответит 403 даже с рабочим маркером.

Заодно стоит проверить `svcdev_host`: на стенде он `svcdev-beta.test`, а
примеры спецификации ГЭПС используют `svcdev-gostapi.test`.
