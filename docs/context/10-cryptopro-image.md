# 10 - Образ с КриптоПро и лицензия

## Два образа, а не один

| Образ | Файл | Что умеет |
| --- | --- | --- |
| `api-gosuslugi-backend:latest` | `api-gosuslugi-backend/Dockerfile` | Всё, кроме подписи. `/version`, `/services`, XML и XSD, каталог. `/hc` и `/status` отдают 503 с `pycades недоступен` |
| `api-gosuslugi-backend:cryptopro` | `api-gosuslugi-backend/Dockerfile.cryptopro` | То же плюс КриптоПро CSP и pycades: подпись, работа с сертификатами, маркер доступа ЕСИА |

Публичный образ намеренно без проприетарных бинарников: его можно собирать и
выкладывать. Образ с КриптоПро собирается локально и наружу не публикуется.

## Что нужно положить рядом

Оба дистрибутива перечислены в `.gitignore` и в репозиторий не попадают:

```
api-gosuslugi-backend/linux-amd64_deb.tgz   дистрибутив КриптоПро CSP для Linux amd64
api-gosuslugi-backend/pycades.zip           исходники pycades
```

Скачиваются с сайта КриптоПро. Сейчас на диске лежит CSP версии `5.0.13000-7`.

## Запуск

```bash
docker compose -f docker-compose.yml -f docker-compose.cryptopro.yml up -d --build
```

Оверлей `docker-compose.cryptopro.yml` меняет только то, что нужно для подписи:
Dockerfile, переменную `CRYPTOPRO_SERIAL`, `KeyPin`, монтирование контейнера
ключа из `key_folder` и публичных сертификатов из
`api-gosuslugi-backend/certs/public`. Всё остальное берётся из базового
`docker-compose.yml`.

Сборка тяжёлая: установка CSP плюс компиляция pycades с boost. Слои кэшируются,
повторные сборки быстрые.

## Лицензия

**Демонстрационный период.** Без серийного номера CSP работает около 90 дней с
момента установки, а установка происходит при сборке образа. Свежесобранный
образ на 2026-08-14 показывает `Expires: 94 day(s), License type: Demo`. Когда
срок вышел, образ пересобирается заново, и отсчёт начинается сначала:

```bash
docker compose -f docker-compose.yml -f docker-compose.cryptopro.yml build --no-cache api
docker compose -f docker-compose.yml -f docker-compose.cryptopro.yml up -d
```

`--no-cache` здесь обязателен: без него слой с установленным CSP возьмётся из
кэша вместе со старой датой установки. Расплата за это - полная пересборка,
включая компиляцию pycades: слой с pycades наследуется от слоя с CSP и
инвалидируется вместе с ним.

**Купленная лицензия.** Серийный номер кладётся в `.env`:

```dotenv
CRYPTOPRO_SERIAL=XXXXX-XXXXX-XXXXX-XXXXX-XXXXX
```

При старте контейнера entrypoint выполняет `cpconfig -license -set` и
переводит CSP с демонстрационной лицензии на купленную, после чего срок
перестаёт иметь значение и пересобирать образ не нужно. Серийный номер живёт
только в переменной окружения и в образ не запекается, поэтому один и тот же
образ годится и для демонстрационного, и для лицензированного стенда.

Состояние лицензии видно в логах при каждом старте:

```bash
docker compose logs api | Select-String cryptopro
```

Образ с проприетарными бинарниками нельзя выкладывать в публичные реестры и
раздавать: лицензия покупается на рабочее место, а не на контейнер.

## Что делает entrypoint

`api-gosuslugi-backend/docker/entrypoint-cryptopro.sh` работает от root и по
шагам:

1. Ставит лицензию, если задан `CRYPTOPRO_SERIAL`, и печатает её состояние.
2. Выставляет права на смонтированный контейнер ключа.
3. Ставит корневые и промежуточные сертификаты из `/certs/public` в `mroot`.
   Личные сертификаты туда не попадают: для них есть `certs/personal`, который
   в образ и в контейнер не монтируется.
4. Ищет ключевые контейнеры через `csptest -keyset -enum_cont` и ставит личный
   сертификат из контейнера в `uMy`.
5. Сбрасывает привилегии и запускает uvicorn от пользователя `app`.

## Проверено на живом стенде 2026-08-14

```
cryptopro: License validity: ... Expires: 94 day(s) License type: Demo.
cryptopro: корневой сертификат установлен: rootca.cer, test_ca_rtk2.cer, ca-root.crt, der.cer
GET /api/hc      200 {"status":"Ok"}
GET /api/status  200 {"Version":"2.0.15000","ModuleVersion":"0.1.44290"}
import pycades   2.0.15000
```

Через nginx фронтенда те же ответы приходят на `http://localhost:50080/api/hc`.

**Подпись проверена целиком**, на тестовом ключе, созданном прямо в контейнере
(как это сделать, описано ниже):

```
csptest -keyset -sign GOST12_256   -> ErrorCode 0x00000000, подпись 64 байта
csptest -keyset -pkverify          -> ErrorCode 0x00000000
то же по изменённым данным         -> 0x80090006 Invalid Signature

pycades SignedData.SignCades(CADESCOM_CADES_BES)  -> подпись получена, 1330 символов base64
pycades SignedData.VerifyCades                    -> проверка успешна
то же по изменённым данным                        -> отклонено
```

64 байта - ровно размер подписи ГОСТ Р 34.10-2012 (256). Отрицательные проверки
важнее положительных: они показывают, что проверяется именно подпись, а не
возвращается заглушка.

Прикладной уровень тоже проходит: `/get_certificates` отдаёт сертификат,
`/set_current_certificate` его выбирает, `/accessTkn_esia` доходит до запроса в
ЕСИА и падает уже там (`Не удалось получить маркер ЕСИА`), потому что API-Key
фиктивный, а сертификат самоподписанный. Криптография при этом отработала.

## Датчик случайных чисел: что работает, а что нет

В образе зарегистрированы два ДСЧ:

| Ник | Что это | Состояние |
| --- | --- | --- |
| `BIO_TUI`, уровень 5 | биологический, просит нажимать клавиши | работает только в интерактивном режиме |
| `CPSD`, уровень 3 | по исходным данным из `/var/opt/cprocsp/dsrf/db1/kis_1` и `db2/kis_1` | не работает, файлов после установки нет |

**Подпись существующим ключом идёт на внутреннем программном датчике и в
headless-контейнере работает.** Это же подтверждает ГОСТ-TLS рукопожатие через
`curl` из состава КриптоПро (рукопожатие требует свежей случайности):

```
/opt/cprocsp/bin/amd64/curl https://svcdev-gostapi.test.gosuslugi.ru/  -> http_code=403, ssl_verify_result=0
/opt/cprocsp/bin/amd64/curl https://www.gosuslugi.ru/                  -> http_code=200
```

403 от тестового контура означает, что TLS состоялся, а отказ пришёл уже от
приложения.

**Строгий ДСЧ нужен только для генерации ключевой пары**, это требование
сертификации. Без него:

```
csptest -keyset -newkeyset -cont '\\.\HDIMAGE\testkey' -provtype 80
Attempting to create a signature key...
Error 0x80090020: An internal error occurred.
```

Одинаково для типов провайдера 75, 80 и 81, от root и от `app`, то есть дело не
в правах: провайдер исправен (`csptest -keyset -verifycontext` даёт
`0x00000000`), контроль целостности проходит без замечаний.

Путь через исходные данные CPSD закрыт: `genkpim` сам требует аппаратный
датчик, причём одинаково и в контейнере, и на Windows-хосте с КриптоПро:

```
genkpim 1000 01d2c1c8 /var/opt/cprocsp/dsrf
write KPIM info OK
Error SetProvParam(PP_USE_HARDWARE_RNG):
```

Файлы, набитые из `/dev/urandom`, и подстановка `/dev/urandom` вместо путей к
гамме тоже не помогают.

Для этого проекта ограничение некритично: ключ приходит от удостоверяющего
центра вместе с контейнером, генерировать его в контейнере приложения не нужно.

## Тестовый ключ и сертификат внутри контейнера

Нужны, только чтобы проверить подпись, пока нет настоящего сертификата
организации. Биологический ДСЧ соглашается работать, если дать процессу
псевдотерминал и подавать в него символы с паузами, как при наборе с клавиатуры,
а после набора энтропии отправлять переводы строки на запрос пароля контейнера.

```sh
# feed.sh: 1200 символов с паузой 0.02 с, затем переводы строки
# genbio.sh: csptest -keyset -newkeyset -cont '\\.\HDIMAGE\biokey' -provtype 80 -protected=none
/tmp/feed.sh | script -qec /tmp/genbio.sh /dev/null
```

Дальше самоподписанный сертификат и его установка:

```sh
csptest -keyset -fmakecert /tmp/self.cer -cont '\\.\HDIMAGE\biokey' -provtype 80 -keytype signature
certmgr -inst -file /tmp/self.cer -cont '\\.\HDIMAGE\biokey' -store uMy -at_signature -to-container
certmgr -install -store mroot -file /tmp/self.cer      # от root, иначе подпись упрётся в недоверенную цепочку
```

Три подводных камня, на которых это ломается:

- `certmgr` по умолчанию ищет ключ обмена и падает с `0x8009000d GetUserKey
  error`. Нужен флаг `-at_signature`.
- Приложение читает сертификаты из хранилища контейнера
  (`CADESCOM_CONTAINER_STORE`), поэтому нужен `-to-container`, установки в `uMy`
  мало.
- Список сертификатов бэкенд загружает один раз при старте, так что после
  установки нужен `docker compose restart api`. Пересоздавать контейнер нельзя:
  тестовый ключ живёт в его записываемом слое и пропадёт.

Такой сертификат годится только для проверки самой подписи. Для реального
обмена с ЕПГУ нужен сертификат организации, см.
[`08-access-and-certificates.md`](08-access-and-certificates.md).

## Грабли сборки

- `cprocsp-rdr-pcsc` требует пакет `pcscd`, поэтому его надо ставить в том же
  слое, где ещё не удалены списки apt.
- В `CMakeLists.txt` из `pycades.zip` путь к заголовкам Python задан константой
  `/usr/local/include/python3.8` обычной `SET`, а не `CACHE`, поэтому
  `-DPython_INCLUDE_DIR` его не перебивает. Dockerfile правит эту строку через
  `sed` под версию Python образа. Если поднимать `PYTHON_VERSION`, проверяйте
  этот момент первым.

## Текущее состояние ключей

Реального ключевого контейнера на диске нет: и `xxx.000` в корне, и
`api-gosuslugi-backend/xxx.000` пустые (файлы `header.key`, `masks.key` и
прочие нулевой длины). Подписывать по-настоящему нечем, пока не придёт
сертификат организации, см.
[`08-access-and-certificates.md`](08-access-and-certificates.md).

Сам механизм подписи при этом рабочий, это проверено на тестовом ключе. Когда
контейнер организации появится, его достаточно положить в папку из `key_folder`:
entrypoint сам выставит права, найдёт контейнер и поставит личный сертификат.
