# epgu-knowledge

Справочная база знаний по подключению к API Госуслуг: маршруты (графы
шагов), источники и практические заметки. Пакет только читает данные, не
обращается к сети и не требует входа.

Маршруты носят справочный характер. Это не исполняемые коннекторы и не
разрешение оператора: подключение к ЕПГУ, ЕСИА и СМЭВ выполняется вручную
у соответствующего оператора. Поле `coverage` маршрута лишь показывает,
какие операции ядра (`capabilities`) относятся к нему.

## Происхождение данных

Набор `epgu-integration-guide` сгенерирован из `guideData.js` клиента
(`repos/public/api-gosuslugi-client/src/components/IntegrationGuide/`).
Это незакоммиченная работа Codex на момент создания: хеш исходника записан
в `dataset.generated_from.sha256`, дата сверки источников в
`dataset.reviewed_at` (`REVIEWED_AT` исходника). Тексты данных взяты
из исходника без правок, поэтому в них могут встречаться длинные тире и
стрелки. Внешние документы только ссылками (`redistribution: link_only`).
Поэтому `scripts/check_text_style.py` пропускает ровно два файла: этот
набор и его копию в клиенте. Остальные проверки на них распространяются.

## Статус

31.10.2026 этапы 0 и 1 приняты как локальный прототип в worktree
`api-mcp-stage1`. Код не закоммичен и не установлен в runtime. Приняты
общая модель знаний, бесплатные HTTP и MCP knowledge и публичный интерфейс
без входа и без backend. Не приняты машинная авторизация, read и operate,
private-модули, развёртывание, внешнее подключение и фактический обмен с API.

1.11.2026 срезы 1-3 этапа 2 приняты как локальный прототип на mocks в
worktree `api-mcp-stage2`: ключи интеграций, привязка оператора и
prepare/approve/execute с политикой целевой операции в плане, моментом
захвата внутри транзакции и журналом шагов. Код не закоммичен и не
установлен в runtime. Не приняты: этап 2 целиком, реальные исполнители и
обмен с Госуслугами, private tenancy, несколько процессов на одну базу,
миграция прежней схемы, человеческий интерфейс одобрения, профили read и
operate в MCP. Ссылки в журнале шагов фильтруются только по формату:
несекретность ссылки обеспечивает исполнитель.

3.11.2026 этап 2 принят целиком как локальный прототип на mocks в worktree
`api-mcp-stage2`. Кроме срезов 1-3 в него вошли HTTP-клиенты интеграций на
Python и JavaScript, административный предпросмотр и одобрение планов в
интерфейсе и неисполняемый каталог MCP-операций. Код не закоммичен и не
установлен в runtime. Это не действующий коннектор Госуслуг. Оговорки:
привязка оператора это ручное утверждение администратора установки, а не
подтверждение полномочий организации через ЕСИА или реестр; одобрять план
может тот же администратор; неизвестный исход сверяется вручную, без
повтора; Python-клиент не даёт общего срока на весь ответ; сигнал контекста
в интерфейсе действует в пределах вкладки; расширения MCP остаются
доверенным кодом процесса. Проверки отсутствия секретов ограничены
форматом и выходными схемами и не являются фильтрацией произвольного
результата. Не приняты: миграция прежней схемы (есть только проект),
несколько процессов на одну базу, реальные исполнители и доступы, ключ
API ЕПГУ, private tenancy, действующие профили read и operate в MCP и
сквозная проверка браузер, backend и внешняя система. Исполняемый код и
данные knowledge после этапа 1 не менялись, менялся только этот статус.

## Ручной маршрут

`data/manual_path.v1.json` со схемой `schema/manual_path.v1.schema.json` это отдельный набор: кабинеты
и консоли TEST и PROD, шаги, поля и пустой шаблон письма. Его читают `load_manual_path()`, HTTP
`GET /v1/knowledge/manual-path`, MCP `knowledge_get_manual_path`, а интерфейс показывает побайтную
копию из `tools/sync_ui_copy.mjs`. Значения организации набор не принимает. Адреса перенесены из
интерфейса и не проверялись на доступность, это записано в `provenance`. Набор `knowledge.v1` от него
не зависит и не менялся.

В manual-path 1.0.1 уточнено, что контур выбирается по подписи TEST или PROD у
ссылки, а не отдельным переключателем интерфейса. UI показывает происхождение
адресов. Для `links_availability=verified` обязательна действительная календарная
дата `links_verified_at`; для `not_verified` она остаётся `null`. Проверка формы
метаданных сама по себе не проверяет внешние кабинеты и не меняет этот статус.

## Копии в клиенте

Клиент (Create React App) не может импортировать файлы за пределами `src/`,
поэтому набор и его схема копируются побайтно в
`api-gosuslugi-client/src/components/IntegrationGuide/`:

```
node tools/sync_ui_copy.mjs          # записать копии
node tools/sync_ui_copy.mjs --check  # код 1, если копия отличается
```

Ответ сервера клиент проверяет этой же схемой (интерпретатор подмножества
JSON Schema в `knowledgeModel.js`; неизвестное ключевое слово схемы считается
ошибкой проверки) и той же ссылочной целостностью, что `validate()`. Сверх
схемы клиент ограничивает раскладку блок-схемы: колонки 0..7, строки 0..39,
не больше одного блока в клетке. Для побайтового сравнения и хешей файлы
набора, схемы, их копий и снимка реестра закреплены в `.gitattributes` как
`eol=lf`.

## Пересборка данных

```
node tools/convert_guide.mjs <путь к guideData.js> src/epgu_knowledge/data/knowledge.v1.json
```

Вывод детерминирован (порядок как в исходнике, отступ 2, перевод строки в

## Интерфейс

```python
from epgu_knowledge import load, limits, KnowledgeBase, KnowledgeError, InvalidDataset, NotFound

kb = load()                       # из данных пакета; load(path) для другого файла
kb.meta()                         # schema_version, content_sha256, dataset, counts
kb.dataset()                      # весь набор в формате knowledge.v1 (копия)
kb.list_routes()                  # краткие записи маршрутов
kb.get_route(route_id)            # маршрут с узлами; NotFound
kb.get_node(route_id, node_id)    # узел + incoming + sources_resolved; NotFound
kb.list_sources(officiality=None) # ValueError при неизвестном значении
kb.get_source(source_id)          # источник + used_by; NotFound
kb.list_notes()
kb.search(query, limit=10, cursor=None, domain=None)
kb.validate()                     # список ошибок схемы и ссылочной целостности
```

Поиск: регистр не важен, `ё` равно `е`, все слова запроса должны найтись
(в title, summary, body, checks, text, section). Порядок: score по
убыванию, затем type, route_id, id. `limit` от 1 до 50, `query` до 200
символов, `cursor` до 200 символов, иначе `ValueError`. Те же пределы
лежат в `epgu_knowledge.limits` и используются в HTTP API v1 и в схемах
MCP tools, поэтому опубликованные ограничения совпадают с проверкой.
`cursor` непрозрачный и привязан к набору данных, запросу и фильтру домена;
чужой или испорченный даёт `ValueError`. При фильтре `domain` заметки и
источники в выдачу не входят (у них нет домена). Все возвращаемые объекты
являются копиями.

Каждый элемент выдачи содержит `source_ids`: явные ссылки этого элемента
на источники. У узла и заметки это их поле `sources`, у источника его
собственный `id`, у маршрута пустой список, потому что в knowledge.v1
у маршрута нет своих ссылок, а источники его узлов ему не приписываются.
Порядок как в наборе, без повторов, только ID, которые открывает
`get_source`. Пустой список значит, что ссылок нет. Ссылка подтверждает
контекст элемента, но не каждое предложение `snippet`. Поля `id` и `type`
не меняются: `id` заметки не является ID источника.

`load()` проверяет схему и ссылочную целостность. При ошибках поднимается
`InvalidDataset` (код `invalid_dataset`, либо `unsupported_version` при
другой `schema_version`), в `errors` первые 20 замечаний, в `total` их
число; повреждённый набор не индексируется и не кэшируется как годный.
Сообщения не содержат локальных путей. `load(path, validate=False)` нужен
только для диагностики: тогда полный список даёт `validate()`. Проверка
не падает на значениях неверного типа (например, id в виде списка): они
попадают в ошибки схемы.
