# Карточка подключения TEST

Карточка разбирает три задачи одного маршрута подключения API ЕПГУ:
запрос полномочия, отказ подписи и следующий шаг к API-ключу. Это
справочные рекомендации проекта, а не регламент оператора. Ссылки в правилах
дают контекст маршрута и требований; они не означают согласование каждой
ветки оператором. Допустимость подключения конкретной организации решает
оператор, карточка этого не устанавливает. PROD этим набором не покрывается.

В публичном интерфейсе выберите «Карточка подключения TEST» (`#connection`).
Разбор работает без сервера установки, входа, запросов к кабинетам и сохранения
отметок. При смене задачи или сбросе отметки очищаются.

## Один набор правил

`src/epgu_knowledge/data/connection_card.v1.json` содержит тексты, 12 признаков,
три задачи и 37 упорядоченных правил. Применяется первое совпавшее правило;
условия допускают только равенство или принадлежность списку. Это не движок
исполнения: нет команд, выражений, произвольных URL или внешних проверок.

Python проверяет схему, ссылки на узлы/источники базы знаний и структуру целей.
Клиент получает побайтовую копию через `tools/sync_ui_copy.mjs`. Схемы входа
и результата HTTP/MCP экспортирует пакет знаний. Версия определения и
`schema_version` присутствуют в результате, ETag определения меняется при
изменении содержимого. Основной набор `knowledge.v1` не изменён.

## Границы результата

Все сведения имеют основание `caller_reported`: их сообщил вызывающий,
система их не проверяла. `reported_yes` — не аттестация оператора. `unknown`
не превращается в отказ или отсутствие события. Проверка `same_context` —
также отметка человека, а не сопоставление реальных идентификаторов.

Карточка не принимает ИНН, OID, названия организаций, ключи, PIN, файлы,
подписи и тексты ответов. Вход закрыт: только цель и известные enum-признаки.
Признаки другой задачи допускаются, но не влияют на её результат и не
включаются в `reported_facts`. Отсутствующие признаки становятся `unknown`.
Статусы готовности, выданные права и разрешения выполнить действия не
формируются. Локальная корректность подписи не доказывает серверный приём;
приём анкеты не доказывает выдачу права; настройка ключа не доказывает вызов API.

## Python, HTTP и MCP

```python
from epgu_knowledge import load_connection_card

result = load_connection_card().evaluate({
    "goal": "obtain_api_key",
    "facts": {"same_context": "reported_yes", "application_submitted": "reported_yes"},
})
assert result["basis"] == "caller_reported"
assert result["rule"]["id"] == "application_pending"
```

- `GET /v1/knowledge/connection-card` — определение, ETag/304, публичное кеширование.
- `POST /v1/knowledge/connection-card/evaluate` — расчёт из отметок, `no-store`
  и на успешном ответе, и на ошибках. Использует существующий публичный бюджет
  запросов; доступ открыт только этим обработчикам, соседние пути не открываются.
- MCP `knowledge_evaluate_connection_card` — тот же расчёт в профиле `knowledge`,
  read-only, без внешней сети. Ошибки входа не отражают переданные значения.

HTTP-клиент передаёт свои enum-отметки серверу расчёта; это отличается от
интерфейса, который считает локально. Не передавайте секреты даже в неизвестных
полях: отказ валидации не отменяет факта отправки запроса вашему HTTP-серверу.

В этот срез не входят опрос кабинетов, доказательства с отметкой времени,
хранение кейсов, выпуск сертификатов, подписание, регистрация доверенности,
выдача/ротация ключей, автоматический запрос поддержки или проверка API.
