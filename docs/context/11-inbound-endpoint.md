# 11 - Приём входящих запросов от ЕПГУ

## Зачем

При регистрации информационной системы в техпортале указываются два адреса:

| Поле в техпортале | Что указывать |
| --- | --- |
| URL системы | `https://<внешний хост>/is` |
| URL для отправки push сообщений | `https://<внешний хост>/push` |

До этого проект умел только ходить в ЕПГУ сам. Теперь есть принимающая сторона.

## Отдельный процесс, а не ещё один маршрут

Приёмник вынесен в самостоятельное приложение
[`inbound.py`](../../api-gosuslugi-backend/inbound.py) и отдельный сервис
compose. Причина простая: наружу смотрит только он, а операторские методы
(сертификаты, маркер доступа, подача заявлений) не должны быть доступны из
интернета даже теоретически.

```
внешний хост -> порт 58080 -> сервис inbound (5001)   только приём
                              сервис api (5000)       только с localhost
```

Проверено: на публичном порту нет ни `/get_certificates`, ни `/accessTkn_esia`,
ни `/inbound/messages`. Любой POST на неизвестный путь просто попадает в журнал.

| Метод и путь | Назначение |
| --- | --- |
| `GET /is`, `GET /` | URL системы: отвечает статусом, мнемоникой и списком точек входа |
| `GET /push` | проба доступности адреса без отправки данных |
| `POST /push` | приём push сообщения, всегда 200 |
| `POST /{любой путь}` | приём и журналирование чего угодно, тоже 200 |
| `GET /health` | проверка живости для compose |

Приёмник отвечает 200 всегда, когда запрос дошёл. Отправитель, который получает
ошибку, начинает копить повторы, а для тестового стенда важнее увидеть сам
запрос, чем отвергнуть его по формату.

## Почему приёмник нестрогий

Контракта входящих push в опубликованных спецификациях API ЕПГУ нет: там
описаны только вызовы, которые ИС делает сама (`/order`, `/push`,
`/push/chunked` и прочие). Проверено поиском по всему снимку каталога в
`docs/api_for_gu`. Поэтому приёмник ничего не разбирает: сохраняет метод, путь,
заголовки, тело и отправителя. Когда станет виден реальный формат, разбор можно
дописать по журналу.

## Журнал

`inbound_store.py`, файл `messages.jsonl` в томе `inbound-data`. Том смонтирован
в приёмник на запись, в операторский API на чтение.

- Тело ограничено `INBOUND_MAX_BODY` (по умолчанию 1 МиБ), лишнее отрезается с
  пометкой `truncated`.
- Файл ротируется при превышении `INBOUND_JOURNAL_MAX_BYTES` (32 МиБ).
- Значения заголовков `Authorization`, `Cookie`, `X-Api-Key` и подобных в
  журнал не пишутся: сохраняется только факт наличия и длина.
- Ошибка записи не мешает ответить отправителю.

Операторские методы на порту 55000: `GET /inbound/messages?limit=` и
`POST /inbound/clear`.

## Вкладка «Входящие»

[`InboundLog.js`](../../api-gosuslugi-client/src/components/InboundLog/InboundLog.js):
поле для внешнего адреса (запоминается в браузере), готовые к копированию
`URL системы` и `URL push`, таблица запросов с автообновлением раз в 5 секунд,
раскрытие строки показывает заголовки, тело и SHA-256.

## Переменные

```dotenv
INBOUND_PORT=58080          # порт наружу
IS_MNEMONIC=                # мнемоника ИС из техпортала, видна на /is
INBOUND_PUBLIC_URL=         # внешний адрес, только для справки на /is
INBOUND_MAX_BODY=1048576    # предел тела запроса
```

## Проверено 2026-08-14

```
GET  :58080/is                  200, status ok, список точек входа
GET  :58080/push                200, code OK
POST :58080/push (JSON статуса) 200, code OK, message_id
POST :58080/api/notify/status   200, XML принят и записан
GET  :55000/api/inbound/messages  обе записи, тела целы, отправитель виден
GET  :58080/get_certificates и прочие операторские методы  405
```

## Чего пока нет

- Проверки подлинности отправителя. Ни подписи, ни списка адресов ЕПГУ в
  документации нет, а придумывать своё до первого реального запроса смысла мало.
  Когда формат станет известен, проверку надо добавить: сейчас на адрес может
  постучаться кто угодно.
- Ответов по существу. Приёмник подтверждает получение, но не выполняет
  действий по содержимому.
