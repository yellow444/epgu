# Внешний адрес информационной системы

В техпортале у информационной системы два адреса, и оба должны вести на наш
приёмник:

| Поле в техпортале | Что вписать |
| --- | --- |
| URL системы | `https://smev.mirasnowfox.ru/is` |
| URL для отправки push сообщений | `https://smev.mirasnowfox.ru/push` или `/message` |

Путь для push придумываем мы, ЕПГУ просто ходит по указанному адресу.
Приёмник принимает POST по любому пути и отвечает 200, а на GET по любому
пути отвечает пробой: проверка доступности из техпортала ходит именно GET, и
405 в ответ выглядел бы как неработающий адрес.

## Схема: туннель не нужен, VPN уже есть

Стенд и VPS соединены существующим VPN. Проверено со стенда:

- VPS виден по VPN как `172.16.10.245`, порты 80 и 443 открыты (это Caddy);
- стенд виден в VPN по адресу `172.16.10.246`;
- приёмник слушает `0.0.0.0:58080` и по VPN-адресу отвечает.

```
ЕПГУ -> https://smev.mirasnowfox.ru/is /push /message  (443, Caddy на VPS)
        VPS, Caddy
        VPN -> 172.16.10.246:58080  приёмник на стенде
        порт 55000 операторский API  наружу не выходит никогда
```

Отдельный SSH-туннель не нужен: VPN уже соединяет VPS и стенд. Caddy ходит на
приёмник прямо по VPN-адресу. VPN этот конфиг не трогает, ничего в нём менять
не нужно.

## Что сделать на VPS

1. A-запись `smev` на адрес VPS уже сделана, домен резолвится в
   `132.243.251.210`. Существующие записи и MX не трогать: почта на том же
   домене остаётся на хостинге.
2. Блок для домена в Caddy: [`Caddyfile`](Caddyfile). Caddy получит
   сертификат сам, если имя резолвится и открыты 80 и 443.

   ```bash
   sudo caddy validate --config /etc/caddy/Caddyfile
   sudo systemctl reload caddy
   ```

   Признак того, что домена в конфиге ещё нет: порт 443 открыт, но TLS не
   устанавливается вовсе. Так и было до этой правки.
3. Чтобы адрес стенда в VPN не менялся, закрепите его за клиентом на
   VPN-сервере. В OpenVPN это каталог `ccd` и строка
   `ifconfig-push 172.16.10.246 255.255.255.0` для этого клиента. Без
   закрепления после переподключения стенда адрес может смениться, и цель в
   Caddy придётся поправить.

Вариант с nginx вместо Caddy остаётся в [`nginx-smev.conf`](nginx-smev.conf) и
[`proxy_is.conf`](proxy_is.conf); там `proxy_pass` тоже идёт на
`172.16.10.246:58080`, а сертификат выпускается отдельно через certbot.

## Что сделать на стенде

1. Открыть порт 58080 для VPN-подсети. VPN-интерфейс у Windows в профиле
   Public, а там входящие по умолчанию закрыты, поэтому VPS до приёмника не
   достучится, пока не разрешить. Команда в PowerShell от администратора,
   разрешает только порт 58080 и только из VPN-сети:

   ```powershell
   New-NetFirewallRule -DisplayName "EPGU inbound (VPN)" -Direction Inbound `
     -Action Allow -Protocol TCP -LocalPort 58080 -RemoteAddress 172.16.10.0/24
   ```

2. В `.env` рядом с `docker-compose.yml`:

   ```dotenv
   INBOUND_PUBLIC_URL=https://smev.mirasnowfox.ru
   INBOUND_TRUSTED_PROXIES=172.16.10.245/32
   ```

   `INBOUND_TRUSTED_PROXIES` обязателен: без него отправителем каждого
   запроса будет виден VPN-шлюз, а не ЕПГУ. Здесь это адрес, с которого
   приходит проксированный запрос от Caddy.

3. Кнопка «Проверить адрес снаружи» на вкладке «Входящие» уйдёт запросом в
   интернет по адресу и покажет, вернулся ли он на приёмник. Это финальная
   проверка всей цепочки.

## Про защиту приёмника

`INBOUND_TOKEN` для этого адреса не годится: ЕПГУ про наш секрет не знает и
заголовок не пришлёт, а приёмник ответит 401. Список сетей
`INBOUND_ALLOW_NETS` тоже нельзя заполнить заранее: опубликованных адресов, с
которых ходит ЕПГУ, в документации нет.

Порядок такой: сначала адрес открыт, работают ограничение частоты и журнал.
После первого настоящего запроса в журнале виден адрес отправителя, и вот
тогда сеть прописывается в `INBOUND_ALLOW_NETS`, а порт закрывается для всех
остальных. Подробности в
[`docs/context/11-inbound-endpoint.md`](../../docs/context/11-inbound-endpoint.md).
