# Из уведомления Госуслуг в задачу: примеры для 1С, Битрикс24 и n8n

Выгрузка уведомлений полезна, когда ее перестают открывать в текстовом редакторе. Хочется увидеть входящую запись в привычной системе: назначить ответственного, связать ее с делом и понять, что делать дальше.

В [EPGU Bell](https://github.com/yellow444/epgu-bell) для этого есть JSON и локальный HTTP API. В этой статье разберу слой получателя: импорт без дублей, заготовки действий для CRM и переход к запросам через отдельный оркестратор API.

Все команды ниже используют два синтетических уведомления. Их можно выполнить без кабинета Госуслуг, внешней CRM и учетных данных. Код примеров открыт; реализация самого сборщика в него не входит.

## Входящая запись и действие над ней

Я разделяю две таблицы. Первая хранит полученное уведомление. Вторая содержит решение, что с ним делать: создать карточку, включить в дайджест или передать оператору.

У записи должны быть ключ подключения, организация, контур и ID источника. Одинаковые по виду сообщения в TEST и рабочем контуре не должны попадать в одну карточку.

Текст сообщения хранится рядом, но не определяет его идентичность. Иначе исправленный заголовок превратится в новое событие, а две разные записи с одинаковым текстом сольются в одну.

## Первый пример: JSON в SQLite

Нужен Python 3.11+. Команды выполняются из новой копии публичного репозитория:

```powershell
git clone https://github.com/yellow444/epgu-bell.git
cd epgu-bell
git checkout v0.2.0-rc.4
$inboxRoot = Join-Path $env:TEMP ('bell-inbox-' + [guid]::NewGuid().ToString('N'))
$importArgs = @(
    'examples/integrations/import_notifications.py',
    '--snapshot', 'examples/snapshot.mock.json',
    '--db', "$inboxRoot/inbox.sqlite3",
    '--organization-id', 'ORG-DEMO',
    '--connection-id', 'demo',
    '--contour', 'test'
)
python @importArgs
python @importArgs
```

Первый импорт добавляет две записи, второй добавляет ноль. Всего в базе остается две. При изменении записи получатель учитывает `last_seen_at`, чтобы запоздавший снимок не переписал более свежие данные.

Тот же [клиент](https://github.com/yellow444/epgu-bell/blob/v0.2.0-rc.4/examples/integrations/import_notifications.py) умеет читать локальный API с пагинацией. Вместо `--snapshot` используются `--base-url` и `--token-file`. Токен принадлежит локальному Bell API, сессия Госуслуг остается у сборщика.

При смене поколения базы сервер возвращает `409 page_snapshot_changed`. В этом случае нужно заново получить согласованную выдачу, а не дописать несколько страниц в уже начатую транзакцию.

## Второй пример: подготовить действия

[Генератор](https://github.com/yellow444/epgu-bell/blob/v0.2.0-rc.4/examples/automation/prepare_actions.py) создает заготовки для Битрикс24, webhook и дайджеста. Используем отдельную базу:

```powershell
$actionsRoot = Join-Path $env:TEMP ('bell-actions-' + [guid]::NewGuid().ToString('N'))
$actionArgs = @(
    'examples/automation/prepare_actions.py',
    '--snapshot', 'examples/snapshot.mock.json',
    '--db', "$actionsRoot/inbox.sqlite3",
    '--output', "$actionsRoot/actions.json",
    '--organization-id', 'ORG-DEMO',
    '--connection-id', 'demo',
    '--contour', 'test',
    '--targets', 'bitrix24,webhook,digest',
    '--entity-type-id', '128',
    '--assigned-by-id', '7'
)
python @actionArgs
python @actionArgs
```

Первый запуск готовит шесть действий: два уведомления для трех получателей. Второй добавляет ноль. Числа 128 и 7 обозначают учебные настройки; для своего портала надо выбрать свой тип смарт-процесса и сотрудника.

В `actions.json` сохраняются `delivery=disabled` и `requires_operator_review=true`. Пример готовит данные для отправителя. Создание карточек и доставка во внешние системы подключаются отдельно. По умолчанию заголовки и тела сообщений в заготовки не включаются; параметр `--include-text` добавляет их явно.

## Битрикс24: сначала найти карточку

Для карточки смарт-процесса формируются описания двух вызовов: поиск через [`crm.item.list`](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-list.html) по внешнему `xmlId`, затем [`crm.item.add`](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-add.html), если карточки нет. Доступные поля своего типа можно проверить методом [`crm.item.fields`](https://apidocs.bitrix24.ru/api-reference/crm/universal/crm-item-fields.html).

После создания нужно сохранить CRM ID в таблице соответствий. Она связывает входящее уведомление с карточкой, ответственным и последующими действиями.

Пара «найти, затем создать» сама по себе не решает гонку двух исполнителей. И `xmlId` не стоит считать серверной гарантией уникальности. В отправителе нужны последовательная обработка по ключу и сверка результата после потери ответа.

Здесь речь о Битрикс24 CRM. Для сайта на «1С-Битрикс: Управление сайтом» нужен свой адаптер.

## 1С: начать с входящего регистра

В поставке есть [пример серверного BSL-модуля](https://github.com/yellow444/epgu-bell/blob/v0.2.0-rc.4/examples/1c/BellReader.bsl): HTTP-запрос, разбор JSON, декодирование текста и таблица уведомлений на выходе. Это заготовка модуля для адаптации и проверки в своей конфигурации, а не готовая EPF или CFE.

Первую прикладную версию я бы строил вокруг регистра входящих. Ключ записи задается контекстом подключения и ID уведомления. Оператор видит заголовок, время получения, состояние разбора и связь с документом. Само уведомление остается источником, решение сотрудника хранится отдельно.

Если сервер 1С находится на другой машине, `127.0.0.1` в серверном модуле указывает именно на сервер 1С. Для первого подключения удобно использовать защищенную папку обмена с JSON. Для HTTP потребуется настроенный доступ к Bell с аутентификацией.

Текущий BSL-пример останавливается, если локальный API сообщает о следующей странице. Для длинной ленты можно воспользоваться опубликованным Python-клиентом и файловым обменом либо дополнить BSL обработкой курсора.

## n8n и ServiceDesk: квитанция после сохранения

Для webhook генератор готовит `event_key` и тело события `bell-event-1`. Тот же ключ предназначен для `Idempotency-Key`.

Практическая последовательность: принять запрос, проверить структуру, сохранить событие с уникальным ключом, выбрать очередь и создать задачу оператору. Подтверждение приема возвращается после сохранения. При повторе получатель находит существующую запись и возвращает ее квитанцию.

В n8n адрес webhook берется из настроенного узла: у него есть отдельные [тестовый и рабочий URL](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/). Сессию Госуслуг или локальный токен Bell передавать в тело события не нужно. Для ServiceDesk действует та же схема с адаптером конкретной системы.

## Как связать уведомление с запросом к API

После разбора оператор может решить, что нужен запрос к услуге. Тогда вызывается отдельный [оркестратор EPGU](https://github.com/yellow444/epgu): подготовить план, показать точные данные, одобрить хеш и исполнить.

Номер заявления сохраняется в карточке задачи. Следующее обращение читает статус по этому номеру. Именно так мы продолжили проверку ФССП в живом TEST после отправки: отдельная операция чтения, без новой подачи.

Получается цепочка: уведомление сохраняется во входящих, человек выбирает действие, API исполняет одобренный запрос, результат возвращается в ту же карточку. LLM можно подключить для предложения категории или следующего шага. Ключ события, права, одобрение и журнал исполнения при этом остаются в обычном коде.

## Что проверить у себя первым

Прогоните один и тот же снимок дважды и убедитесь, что входящих записей и задач не стало больше. Затем измените организацию, оборвите чтение посередине и смоделируйте потерю ответа от получателя. Эти три случая быстро показывают, готов ли интеграционный слой к работе за пределами демонстрации.

Команды, контракты и варианты продолжения собраны в [руководстве автоматизаций Bell](https://github.com/yellow444/epgu-bell/blob/v0.2.0-rc.4/docs/AUTOMATION_RECIPES.md).
