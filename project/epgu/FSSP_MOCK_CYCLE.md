# ФССП 60010153: полный цикл на mocks через HTTP API и MCP

Это воспроизводимый синтетический сценарий запроса о наличии исполнительного
производства. Он использует настоящий backend, вход, ключ интеграции,
предпросмотр и одобрение плана, механизм исполнения, XML-построитель,
официальную XSD запроса, ZIP и клиент SDK. Ответы ЕПГУ подменены
`httpx.MockTransport`. Для Госуслуг не открывается ни одного сетевого соединения.

Документ `mock-result.xml` имеет наш демонстрационный формат. Это не формат
реального ответа ФССП и не подтверждение подключения к TEST или PROD.

## Запуск

Нужны Python с зависимостями backend и MCP extra `operations`. Из каталога
`project/api-gosuslugi-backend`, в своём виртуальном окружении:

```powershell
python -m pip install -r requirements-test.txt -e ../mcp-server[operations]
python ../examples/fssp_mock_cycle.py --output C:/temp/epgu-fssp-mock-run-1
```

Каталог результата должен быть пустым и находиться вне Git. Его нельзя
направлять на данные существующей установки. Для повторного запуска выберите
другой пустой каталог.

Скрипт создаёт собственную базу, синтетического администратора и ключ
интеграции нашей установки. API-Key Госуслуг и полномочия оператора этим
не выдаются. Backend слушает только `127.0.0.1` на свободном временном порту.
Жизненный цикл рабочего приложения с почтой и криптопровайдером отключён.
Никакие файлы ключей или пользовательские сертификаты не подключаются.

## Что происходит

1. Через HTTP выполняются вход и выпуск отдельного ключа интеграции.
2. Форма проходит `/fssp/preview`: создаются `req.xml` и `piev_epgu.xml`,
   бизнес-запрос проверяется по XSD.
3. Через `/v1/operations/plans` создаётся план для
   `mock.fssp.60010153.cycle`. Семантическая проверка исполнителя проходит до
   записи плана и резервирования номера. Разрешена только фиксированная
   синтетическая форма; другие услуги, вложения и неоднозначный JSON отклоняются.
4. Отдельная сессия администратора читает точные байты плана, проверяет хеш
   и одобряет его через `/v1/admin/operations/plans/{id}/approve`.
   В этом примере роль человека исполняет тестовый сценарий. MCP и ключ
   интеграции одобрять план не могут.
5. Исполнитель через настоящий `EpguClient` резервирует номер, подставляет
   его в XML, отправляет одночастный ZIP, получает конечный статус и скачивает
   ZIP результата. Каждому HTTP-вызову соответствует запись в журнале.
6. Результат проверяется, сохраняется в плане и читается через API.
   Повтор успешного execute возвращает сохранённый результат без повторной подачи.
7. Та же цепочка повторяется через отдельный процесс stdio MCP. Его
   `plan_prepare`, `plan_execute` и `plan_get` обращаются к тому же локальному
   backend по HTTP. После execute результат читается отдельным plan_get;
   автоматического скрытого чтения нет.
8. Ключ отзывается через API, проверяется отказ с отозванным ключом,
   файл секрета удаляется и собственный backend останавливается.

В каталоге результата остаются `receipt.json`, синтетическая база и две
папки `http/` и `mcp/` с запросами и mock-документом. В receipt указаны шаги,
размеры файлов, SHA-256 результата, отзыв ключа и остановка backend.
Секрет ключа и пароль туда не выводятся. На Windows этот пример не аттестует
ACL файлов настоящих секретов; здесь используются только временные mock-данные.

## Что остаётся выключенным

Обычный `app.py` не регистрирует mock-исполнитель. Обычный MCP CLI сохраняет
профиль `knowledge`; `read` и `operate` не включаются. Для демонстрации
используется явный запуск `python -m epgu_mcp.mock_fssp_cycle` с параметрами
собственного локального backend и временного файла ключа. Запускающий скрипт
задаёт их сам. Демонстрационный MCP нельзя направлять на рабочую установку.

Реальная возможность `fssp.submit` не получает машинного допуска. Не меняются
политики членства, лицензий, доверия сертификатам и одобрения. Отсутствие
подписи в этом сценарии следует из существующего локального контракта
60010153; проверка реального приёма услуги остаётся отдельной внешней приёмкой.

## Отказы

Проверяются запрет execute до одобрения, неверная форма до записи плана,
отклонение PROD-контекста, потеря ответа на каждом из четырёх шагов, неверный
номер заявления, неконечный статус и неверный документ результата.

При потере ответа план получает `unknown`, сохраняет известные завершённые
шаги и начатый вызов с неизвестным исходом. Автоматической повторной отправки
нет. При неконечном статусе этот ограниченный пример останавливается без
документа; долгий опрос и последующее продолжение реального заявления здесь
не реализованы.
