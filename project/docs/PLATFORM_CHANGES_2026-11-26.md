# Изменения ЕСИА, API ЕПГУ и смежных платформ

Сверка 26 ноября 2026 года. Это обзор документации и опубликованных правил,
а не подтверждение выданного конкретной ИС доступа. Вход пользователя ЕСИА,
получение машинного маркера, допуск к услуге и подпись документа проверяются
отдельно. Согласие пользователя не заменяет согласование подключения ИС.

## Вход через Госуслуги на коммерческих ресурсах

Эксперимент с использованием ЕСИА для социальных сетей, заключения договоров,
сервисов торговли и поиска работы продлен до 31 декабря 2030 года
постановлением Правительства РФ от 07.11.2026 № 1473. Это развитие существующего
эксперимента, а не впервые появившаяся в 2026 году технология входа.

Для сайта по-прежнему нужны регистрация ИС, согласованный сценарий и права
доступа. Продление срока не открывает любому произвольному сайту все данные
профиля и не дает ему полномочия API ЕПГУ.

Источники: [разъяснение прокуратуры от 13.11.2026](https://epp.genproc.gov.ru/ru/proc_42/activity/legal-education/explain/e8723161/),
[регламент ЕСИА](https://digital.gov.ru/documents/reglament-informaczionnogo-vzaimodejstviya-esia).

## Переходный период по безопасности до 2027 года

В письме Минцифры от 08.10.2025 № ОК-П24-97784 прямо указаны сервисы ЕСИА на
OAuth 2.0 и OpenID Connect 1.0. Для ранее подключенных ИС установлен переход
на приложение Д методических рекомендаций до 1 января 2027 года. Новое
подключение должно соответствовать требованиям при подключении.

В письме названы защита канала сертифицированными СКЗИ класса не ниже КС3,
применение средства электронной подписи соответствующего класса и оценка
влияния использующего его технического решения. Перечень типовых решений
находится в приложении Д. Нарушение требований может привести к ограничению
доступа. Проверка конкретного исполнения, состава ИС и применимости требований
требует сверки с оператором; наличие КриптоПро само по себе не подтверждает
соответствие всей установки.

Наш EPGU не заявляется типовым решением из этого перечня. Прохождение mocks,
наличие OAuth-клиента или Docker-образа не заменяет предусмотренную процедуру.
Для Bell с пользовательской сессией нельзя автоматически переносить все
условия прямого OAuth/OIDC-подключения без определения его реальной схемы.

Первичный документ: [письмо Минцифры, копия НАУФОР](https://naufor.ru/download/2026/MZ_08102025.pdf).
[Публикация письма Банка России от 06.02.2026](https://naufor.ru/tree.asp?n=31662).

## Технические изменения ЕСИА

В официально опубликованных методических рекомендациях 3.66 есть изменения,
которые важно учитывать при переносе старых примеров:

- В версии 3.58 уточнен формат Base64URL без символов заполнения `=`.
- В версии 3.65 уточнено кодирование `timestamp` согласно RFC 3986.
- В версии 3.66 из описания раздела Б.5 исключено значение длины хэш-кода
  512 бит, исправлены примеры заголовков маркеров и описание `scope_org`.
  Это изменение конкретного формата проверки маркеров; его нельзя трактовать
  как отзыв всех сертификатов с любым 512-битным алгоритмом.
- Описаны API Gateway и механизм делегированной аутентификации/авторизации.
  Сноска о Gateway в опубликованной версии по-прежнему говорит об опытной
  эксплуатации и предоставлении возможности после 1 июля 2026 года. Одной
  этой сноски недостаточно, чтобы объявить Gateway доступным каждой ИС.

[Карточка официальных методических рекомендаций 3.66](https://sc.digital.gov.ru/documents/-/document_library/03jzkn2sfJTq/view_file/10417441).

## Новый кабинет подключения API ЕПГУ

Инструкция ЛК API описывает доступный с 2026 года кабинет вендора:
организации, информационные системы, услуги, заявки и подзадачи подключения.
Предусловие доступа в этой инструкции: организация вендора, ЮЛ или ИП,
зарегистрирована в продуктивной ЕСИА. Руководитель имеет доступ по умолчанию,
другим сотрудникам нужно соответствующее полномочие. Доступ к кабинету нельзя
выдавать за допуск ИС к выбранной услуге.

В актуальной карточке каталога размещена общая спецификация API ЕПГУ 1.15.
В ней отдельно описаны маркеры для ФЛ и для ЮЛ/ИП, ГОСТ TLS, подключения через
СМЭВ 4 и СВОКС. Формат и допуск проверяются также по спецификации конкретной
услуги. Наличие общего scope `api-order` не подтверждает настройку всех услуг.

Источники: [инструкция ЛК API](https://gu-st.ru/content/partners/api_for_gu/Instrukciya_LK_API_v1.docx),
[спецификация 1.15](https://gu-st.ru/content/partners/api_for_gu/Specifikaciya_API_EPGU_v1_15.docx),
[официальный каталог](https://partners.gosuslugi.ru/catalog/api_for_gu).

## MAX

В текущей документации Bot API требуется `platform-api2.max.ru`. Токен
передается в заголовке `Authorization: <access_token>`; query-параметр с токеном
больше не поддерживается. Документация также сообщает о прекращении поддержки
`GET /chats` с июня 2026 года и ограничении `POST /chats/{chatId}/members`
с 9 сентября 2026 года.

Bot API, мини-приложение, цифровой ID и ЕСИА являются отдельными интеграциями.
Токен бота MAX не дает доступ к Госуслугам или их уведомлениям. В наших
публичных гайдах есть маршруты и ссылки; готовый проверенный живой коннектор
ко всем этим возможностям этой заметкой не заявляется.

Источник: [официальный MAX Bot API](https://dev.max.ru/docs-api).

## Цифровой рубль

Банк России сообщил о старте использования с 1 сентября 2026 года у крупнейших
банков и розничных компаний. Дальнейшее подключение идет по этапам, включая
2027 и 2028 годы. Критерии применимости и исключения следует проверять в
актуальных ответах Банка России для конкретного участника.

Интеграция идет через инфраструктуру участников платформы, в частности банки.
Получение доступа к API ЕПГУ не подключает платежи цифровым рублем. Наши mocks
ФССП и Bell не проверяют платежи или подключения к банковской платформе.

Источники: [старт использования](https://cbr.ru/press/event/?id=32802),
[ответы Банка России](https://cbr.ru/faq/dr/).
