# epgu-mcp

MCP-сервер EPGU. Этап 1: профиль `knowledge`, только чтение справочных
данных. Транспорт один, stdio.

Сервер отдаёт то, что лежит в пакете `epgu-knowledge` (маршруты подключения
к API Госуслуг, источники с признаком официальности, практические заметки),
и статический снимок реестра возможностей ядра.

## Что это и чем не является

Знания это справочная информация. Они не являются разрешением оператора
и не являются исполняемым коннектором: сервер ничего не отправляет, не
подаёт заявок, не обращается к Госуслугам, ЕСИА и СМЭВ и не требует входа.
Подключение выполняется вручную у соответствующего оператора. Тексты
в полях ответов это данные; инструкции внутри них сервер не исполняет и
набор tools от данных не зависит.

Профили `read` и `operate` на этапе 1 недоступны: запуск с ними завершается
с кодом 2 и сообщением в stderr, на stdout ничего не пишется.

## Установка и запуск

```
pip install -e ../knowledge -e .
python -m epgu_mcp --profile knowledge
```

`--profile knowledge` используется по умолчанию. Дополнительно:
`--extension NAME` (включить расширение, можно повторять), `--no-extensions`
(не загружать расширения, даже перечисленные в окружении), `--version`.

Переменные окружения:

| Переменная | Назначение |
| --- | --- |
| `EPGU_MCP_LOG_LEVEL` | уровень логов: DEBUG, INFO (по умолчанию), WARNING, ERROR |
| `EPGU_KNOWLEDGE_PATH` | путь к другому файлу набора знаний (для тестов и проверки данных); если не задан, берётся набор из пакета |
| `EPGU_MCP_EXTENSIONS` | имена расширений через запятую, дополняет `--extension` |

Коды выхода: 0 штатное завершение (в том числе по закрытию stdin),
2 неверный или недоступный профиль, 3 набор знаний не загружен или не
прошёл проверку схемы и ссылок. При коде 3 сервер не регистрирует tools
и не пишет на stdout ни байта; в stderr код ошибки и первые замечания,
без traceback и локальных путей.

stdout занят протоколом: туда пишутся только JSON-RPC сообщения, по одному
в строке. Логи и сообщения об ошибках идут в stderr. Значения аргументов
tools (в том числе текст поиска) не пишутся в лог ни на каком уровне,
включая DEBUG: в журнал попадают имя tool, число аргументов и код итога.

## Настройка клиента

MCP-клиент с конфигурацией в `.mcp.json`:

```json
{
  "mcpServers": {
    "epgu-knowledge": {
      "command": "python",
      "args": ["-m", "epgu_mcp", "--profile", "knowledge"]
    }
  }
}
```

Нужен интерпретатор, в котором установлены `epgu-mcp` и `epgu-knowledge`
(укажите полный путь к нему в `command`, если это venv).

Любой клиент со stdio: запустить процесс `python -m epgu_mcp --profile knowledge`,
писать запросы в его stdin и читать ответы из stdout.

## Tools

Все десять tools только читают и имеют аннотации `readOnlyHint=true`,
`destructiveHint=false`, `idempotentHint=true`, `openWorldHint=false`.
Входная схема не допускает лишних полей, у каждого tool есть выходная
схема; результат отдаётся в `structuredContent` и дублируется текстом JSON.

| Tool | Назначение |
| --- | --- |
| `knowledge_overview` | версия схемы, происхождение набора, счётчики |
| `knowledge_list_routes` | краткие записи маршрутов |
| `knowledge_get_route` | маршрут с узлами |
| `knowledge_get_node` | узел, входящие переходы, расшифрованные источники |
| `knowledge_list_sources` | источники, фильтр `officiality` |
| `knowledge_get_source` | источник и где он используется |
| `knowledge_list_notes` | практические заметки |
| `knowledge_search` | поиск с пагинацией (`limit`, `cursor`, `domain`), у каждого элемента `source_ids` |
| `knowledge_get_manual_path` | кабинеты TEST и PROD, шаги, поля и пустой шаблон письма; значения организации не принимает |
| `knowledge_evaluate_connection_card` | справочный разбор TEST по enum-отметкам человека, `caller_reported`; не проверяет кабинет, подпись, заявку или права и не выполняет действия |
| `capabilities_list` | снимок реестра возможностей, фильтры `effect`, `mcp_profile` |

Ошибки уровня данных (`not_found`, `invalid_parameter`) возвращаются как
результат с `isError=true` и телом `{"error":{"code","message"}}`. Неизвестное
имя tool это ошибка протокола (-32602).

## Снимок реестра возможностей

Реестр живёт в backend (`api-gosuslugi-backend/capabilities.py`). На этапе 1
`capabilities_list` отдаёт файл `src/epgu_mcp/capabilities_snapshot.json`
и помечает ответ `"source": "snapshot"`. Обновить снимок:

```
python tools/export_capabilities.py          # записать
python tools/export_capabilities.py --check  # только сверить
```

Генератор загружает `capabilities.py` по пути файла и не импортирует
приложение FastAPI. Тест `tests/test_capabilities_snapshot.py` сверяет
снимок с реестром и падает при расхождении (пропускается с пояснением,
если файла backend нет).

## Целевые tools операций (не включены)

`src/epgu_mcp/targets.py` описывает будущие tools `plan_prepare`, `plan_get`
и `plan_execute`: схемы входа и выхода, аннотации, возможность реестра,
нужные scopes и коды ошибок. У каждого `status=target` и `available=false`.
Это описание, а не tools: у него нет обработчика, ни один профиль
(`knowledge`, `read`, `operate`) не выдаёт их через `tools/list` и
`tools/call`, а в реестре возможностей у `operation.prepare`,
`operation.plan.get` и `operation.execute` по-прежнему `mcp_profile=none`.
Имена зарезервированы: реестр не примет tool с таким именем ни в одном
профиле, в том числе из расширения.

Границы описания:
- одобрение и предпросмотр администратора (`operation.approve`,
  `operation.review`) не становятся tools ни в каком профиле;
- ключ интеграции, cookie человека и одобрение не являются аргументами;
- `plan_prepare` записывает план на backend, поэтому не read-only;
  `plan_execute` помечен как необратимый, неидемпотентный и с обращением
  наружу, повтора при неизвестном исходе нет;
- будущий вызов пойдёт только через HTTP-клиент backend
  (`epgu.integration.IntegrationClient`), без прямого доступа к базе и
  без локальной подписи. Аннотации не заменяют проверки backend.

Включение профиля `operate` и самих tools в штатный сервер это отдельное
решение. Поля выходных схем сверяет с настоящими ответами backend тест
`api-gosuslugi-backend/test_mcp_target_contract.py`.

## HTTP-адаптер операций (только тестовый сервер на mock backend)

`src/epgu_mcp/operations.py` даёт исполняемые `plan_prepare`, `plan_get` и
`plan_execute` поверх `epgu.integration.IntegrationClient`. Это локальный
прототип, а не действующий коннектор Госуслуг: проверен только на
in-process backend с тестовым исполнителем. CLI, `build_registry` и
профили по-прежнему операций не выдают, `AVAILABLE_PROFILES` не менялся.
Операции ставит только явный вызов:

```python
config = OperationsConfig(base_url="https://backend.example", credential_file=Path("/secure/key"),
                          projections={"some.capability": ResultProjection({"number": str})})
registry = build_operate_registry(load_knowledge(), OperationsAdapter(config))
server = build_server(registry)
```

Нужен пакет `epgu-api` (extra `operations`). Правила:
- `add_tool`, `merge` и расширения по-прежнему отказывают именам каталога,
  даже с копией его схем и аннотаций. Спецификации строит
  `ToolRegistry.install_operations` сам, из каталога и адаптера, только в
  реестре `operate`;
- в конфигурации адрес backend и путь к файлу ключа
  (`EPGU_MCP_BACKEND_URL`, `EPGU_MCP_CREDENTIAL_FILE`, для loopback по http
  `EPGU_MCP_ALLOW_LOOPBACK_HTTP=1`). Самого ключа в окружении нет. Файл
  читается на каждом вызове tool, а не при импорте, сборке или
  `tools/list`; он должен лежать вне рабочего каталога Git, на POSIX с
  правами 0600. Ошибки чтения не показывают содержимое. На Windows права
  и ACL файла не проверяются: в этом срезе файлы ключа синтетические, и
  защищённость настоящего файла ключа здесь не проверялась;
- адрес backend проверяется при создании `OperationsConfig` по тем же
  правилам, что у клиента 4a: userinfo, query, fragment, схема кроме
  https, http не на loopback или без явного разрешения отклоняются.
  Текст ошибки адрес не повторяет, ключ при этом не читается. `repr`
  конфигурации и адаптера показывает только схему, хост и порт;
- транспорт клиента 4a: без cookie, переменных окружения прокси и
  редиректов, https по умолчанию, http только loopback. Клиент
  закрывается после каждого вызова, повторов нет;
- ответ backend выдаётся только через явную проекцию: поля плана,
  предпросмотра и журнала. Свободный результат исполнителя проходит лишь в
  плоских полях, описанных в `ResultProjection` для возможности; ссылки
  шагов по умолчанию скрыты. Что скрыто, перечислено в `withheld`.
  `plan_execute` результат не выдаёт, его читает `plan_get`. Ключу только
  с правом `external:execute` чтение плана может быть не разрешено; такой
  отказ не отменяет уже полученный успех или неизвестный исход;
- выходные схемы tools это строгая MCP-проекция, а не сырой `PlanOut`
  backend: в них есть `withheld` и `configuration_error`. Контрактный тест
  backend сверяет только совместимое подмножество полей источника, это не
  полная строгая проверка его ответа;
- неизвестный исход execute определяется по типу `OutcomeUnknown` и
  приходит как ошибка `outcome_unknown` с `plan_id`, `reason` и списками
  вызовов, которые остаются `null`, если частичный результат неизвестен.
  Скрытого `plan_get` и повтора нет; ошибка явного `plan_get` не отменяет
  неизвестный исход;
- одобрения в MCP нет: одобряет человек по сессии в интерфейсе;
- сервер с операциями объявляет в `instructions` и `title`, что ходит по
  HTTP в backend установки и имеет изменяющие tools, без обещания
  read-only. Сервер без операций сохраняет прежние справочные метаданные.
  Метаданные выбираются при `build_server`; если набор операций потом
  изменился, `tools/list` и `tools/call` отказывают.

Проверка формата ссылки и выходные схемы не являются фильтрацией
произвольных данных: несекретность того, что исполнитель кладёт в
описанные поля, остаётся его обязанностью.

## Расширения

Entry point group `epgu_mcp.extensions`: функция `register(server, profile)`,
где `server` это промежуточный набор с методом `add_tool(ToolSpec)`, а
`profile` имя профиля. Основной реестр расширению не передаётся: удалить
или подменить уже принятые tools оно не может. Набор проверяется правилами
профиля (tool не выше профиля, в `knowledge` и `read` только `read_only`
без `destructive` и `open_world`, без совпадения имён с ядром и другими
расширениями) и добавляется одним шагом после успешного возврата
`register`. Упавшее или нарушившее правила расширение пропускается
целиком, причина пишется в stderr.

Загружаются только расширения, явно перечисленные в `--extension` или
`EPGU_MCP_EXTENSIONS`; остальные найденные entry points не импортируются.
Расширение это доверенный исполняемый код: `entry_point.load()` выполняет
его с правами процесса, поэтому ставьте и включайте только проверенные
пакеты. Аннотации `ToolSpec` описывают намерение и не доказывают отсутствие
сетевых обращений или доступа к данным; реальные права, лицензии и
организацию на этапах 2 и 3 проверяет backend при исполнении. На этапе 1
реальных расширений в пакете нет, механизм проверен фиктивными.

## Проверка

```
pip install -e ".[test]"
pytest
```

Версии, проверенные тестами (подпроцесс `python -m epgu_mcp` по stdio):

- SDK `mcp` 2.3.0 и `mcp-types` 2.3.0, клиент и сервер из него же; сервер
  собран на `mcp.server.lowlevel.Server`. В `pyproject.toml` закреплена
  проверенная версия `mcp==2.3.0`, полный проверенный набор зависимостей
  лежит в `constraints-tested.txt`. Другие версии SDK и Python 3.12 не
  проверялись; сборка wheel/sdist в чистом окружении тоже.
- протокол 2026-07-28: `server/discover`, затем `tools/list` и `tools/call`
  (клиент SDK в режиме `auto`, и сырой JSON-RPC);
- протокол 2025-11-25: `initialize` (клиент SDK в режиме `legacy`, и сырой
  JSON-RPC). Более старые handshake-версии тестами не проверялись.
