# 11 - Приём входящих запросов от ЕПГУ

## Зачем

При регистрации информационной системы в техпортале указываются два адреса:

| Поле в техпортале | Что указывать |
| --- | --- |
| URL системы | `https://<внешний хост>/is` |
| URL для отправки push сообщений | `https://<внешний хост>/push` |

До этого проект умел только ходить в ЕПГУ сам. Теперь есть принимающая сторона.

## Отдельный процесс, а не ещё один маршрут

Приёмник вынесен в самостоятельное приложение
[`inbound.py`](../../api-gosuslugi-backend/inbound.py) и отдельный сервис
compose. Причина простая: наружу смотрит только он, а операторские методы
(сертификаты, маркер доступа, подача заявлений) не должны быть доступны из
интернета даже теоретически.

```
внешний хост -> порт 58080 -> сервис inbound (5001)   только приём
                              сервис api (5000)       только с localhost
```

Проверено: на публичном порту нет ни `/get_certificates`, ни `/accessTkn_esia`,
ни `/inbound/messages`. Любой POST на неизвестный путь просто попадает в журнал.

| Метод и путь | Назначение |
| --- | --- |
| `GET /is`, `GET /` | URL системы: статус и список точек входа |
| `GET /push` | проба доступности адреса без отправки данных |
| `POST /push` | приём push сообщения, всегда 200 |
| `POST /{любой путь}` | приём и журналирование чего угодно, тоже 200 |
| `GET /health` | проверка живости для compose |

Приёмник отвечает 200 всегда, когда запрос дошёл. Отправитель, который получает
ошибку, начинает копить повторы, а для тестового стенда важнее увидеть сам
запрос, чем отвергнуть его по формату.

## Почему приёмник нестрогий

Контракта входящих push в опубликованных спецификациях API ЕПГУ нет: там
описаны только вызовы, которые ИС делает сама (`/order`, `/push`,
`/push/chunked` и прочие). Проверено поиском по всему снимку каталога в
`docs/api_for_gu`. Поэтому приёмник ничего не разбирает: сохраняет метод, путь,
заголовки, тело и отправителя. Когда станет виден реальный формат, разбор можно
дописать по журналу.

## Кто может стучаться

[`inbound_guard.py`](../../api-gosuslugi-backend/inbound_guard.py), три рубежа:

| Переменная | Что делает | По умолчанию |
| --- | --- | --- |
| `INBOUND_ALLOW_NETS` | список сетей CIDR, с которых принимаем | пусто, принимаем со всех |
| `INBOUND_TOKEN` | общий секрет в заголовке `X-Inbound-Token`, только латиница | пусто, не спрашиваем |
| `INBOUND_RATE_PER_MINUTE`, `INBOUND_RATE_BURST` | частота с одного адреса | 60 в минуту, всплеск 20 |
| `INBOUND_RATE_GLOBAL_PER_MINUTE` | частота на весь приёмник | 600 в минуту |
| `INBOUND_TRUSTED_PROXIES` | чьему `X-Forwarded-For` верим | пусто, берём адрес сокета |
| `INBOUND_PUBLIC_IDENTITY` | показывать ли мнемонику и адрес ИС на `/is` | 0, не показывать |

Отказы (403, 401, 429, 413) в журнал не пишутся, только считаются и попадают в
лог. Иначе поток отказов сам вытеснит из журнала то, ради чего он заведён.

Перед публикацией адреса в техпортале нужно задать `INBOUND_ALLOW_NETS` или
`INBOUND_TOKEN`. Пока ни одно не задано, приёмник пишет об этом при старте.

## Журнал

`inbound_store.py`, файл `messages.jsonl` в томе `inbound-data`. Том смонтирован
в приёмник на запись, в операторский API на чтение.

- Тело ограничено `INBOUND_MAX_BODY` (по умолчанию 1 МиБ). Если размер объявлен
  в `Content-Length` и он больше - отвечаем 413, не читая. Если не объявлен -
  принимаем и режем с пометкой `truncated`.
- В журнал попадает не больше `INBOUND_JOURNAL_BODY_MAX` (64 КиБ) тела; в записи
  остаются настоящий размер, `body_stored` и SHA-256, так что обрезка проверяема.
- Файл ротируется при превышении `INBOUND_JOURNAL_MAX_BYTES` (32 МиБ), запасных
  файлов `INBOUND_JOURNAL_KEEP` (3). Журнал остаётся окном, а не архивом:
  сообщения нужно забирать, а не хранить в нём.
- Значения заголовков `Authorization`, `Cookie`, `X-Api-Key` и подобных в
  журнал не пишутся: сохраняется только факт наличия и длина.
- Ошибка записи не мешает ответить отправителю.

Операторские методы на порту 55000: `GET /inbound/messages?limit=` и
`POST /inbound/clear`.

## Вкладка «Входящие»

[`InboundLog.js`](../../api-gosuslugi-client/src/components/InboundLog/InboundLog.js):
поле для внешнего адреса (запоминается в браузере), готовые к копированию
`URL системы` и `URL push`, таблица запросов с автообновлением раз в 5 секунд,
раскрытие строки показывает заголовки, тело и SHA-256.

## Переменные

```dotenv
INBOUND_PORT=58080             # порт наружу
IS_MNEMONIC=                   # мнемоника ИС из техпортала
INBOUND_PUBLIC_URL=            # внешний адрес, для справки
INBOUND_MAX_BODY=1048576       # предел тела запроса
INBOUND_ALLOW_NETS=            # сети отправителей, CIDR через запятую
INBOUND_TOKEN=                 # общий секрет, openssl rand -hex 32
INBOUND_TRUSTED_PROXIES=       # сети своего обратного прокси
INBOUND_RATE_PER_MINUTE=60
INBOUND_RATE_BURST=20
INBOUND_RATE_GLOBAL_PER_MINUTE=600
INBOUND_JOURNAL_BODY_MAX=65536
INBOUND_JOURNAL_KEEP=3
INBOUND_PUBLIC_IDENTITY=0
```

## Проверено 2026-08-16, обстрел своего же порта

Так выглядел приёмник до защиты и после неё. Стенд наш, стреляли по себе.

| Проверка | Было | Стало |
| --- | --- | --- |
| 70 запросов по 1 МБ за 5 с | журнал стёрт целиком, вместе с настоящим сообщением | 200 запросов: 19 приняты, 181 отклонён с 429, настоящее сообщение на месте |
| занято на диске при обстреле | 62 МБ | 1.3 МБ |
| тело 2 МБ | принято и молча обрезано | 413 до чтения тела |
| тела в журнале от запроса 900 КБ | 900 КБ | 64 КБ, размер и хэш от целого |
| `X-Forwarded-For: 8.8.8.8` от постороннего | записан как адрес отправителя | записан адрес сокета |
| `GET /is` | мнемоника ИС и внешний адрес | только статус и точки входа |
| заголовок `Server` | `uvicorn` | не отдаётся |

## Чего пока нет

- Проверки подписи отправителя. Ни подписи, ни списка адресов ЕПГУ в
  документации нет. Список сетей и общий секрет закрывают порт настолько,
  насколько это возможно без контракта; настоящую проверку добавим, когда
  увидим первый реальный запрос.
- TLS. Порт отдаёт HTTP, а в техпортале указывается `https://`. Нужен
  обратный прокси с сертификатом на внешнем хосте; он же должен попасть в
  `INBOUND_TRUSTED_PROXIES`, иначе адрес отправителя будет виден как адрес
  прокси.
- Ответов по существу. Приёмник подтверждает получение, но не выполняет
  действий по содержимому.
