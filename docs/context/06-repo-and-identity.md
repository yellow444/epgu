# 06 - Репозиторий, ветки и авторство

## Где живёт проект

Рабочая копия: `F:\source\repos\yellow444\epgu`.
Единственный remote:

```
origin  https://github.com/yellow444/epgu
```

Раньше рядом существовала посторонняя папка `F:\source\repos\epgu` без remote,
на ветке `develop`, с чужой подписью в истории. Их легко было перепутать, часть
работы по ошибке уехала туда. Папка удалена 2026-06-28, всё нужное из неё
перенесено (в частности, каталог `docs/context`). Если она где-то появится
снова, это не рабочая копия.

Прежние remote `QuadYellow/epgu` и `origin-old` удалены, упоминания `knightmc` и
`QuadYellow` из файлов вычищены.

Локальный `git config` в этой папке выставлен на `Maksim <yellow444@gmail.com>`,
чтобы коммиты не уходили под другую подпись. Глобальный конфиг исправлен там же
2026-07-31.

### Зеркало в приватный репозиторий

Основной репозиторий один: `yellow444/epgu`. Копия уезжает в приватный
репозиторий второго аккаунта, remote называется `mirror`.

```
origin  https://github.com/yellow444/epgu          основной
mirror  https://github.com/QuadYellow/epgu.git     приватная копия
```

Авторство от зеркала не зависит: в коммитах остаётся `Maksim
<yellow444@gmail.com>`, зеркало лишь хранит те же объекты в другом месте.
Отправка отдельной командой, чтобы копия не уезжала случайно:

```bash
sh scripts/push_mirror.sh
```

Один шаг остаётся ручным: `QuadYellow` это обычный пользовательский аккаунт, а
не организация, поэтому чужим токеном там нельзя ни создать репозиторий, ни
получить право записи. Владелец аккаунта должен создать приватный `epgu` и
добавить `yellow444` в Collaborators с правом записи. После этого push пойдёт
уже настроенными учётными данными, второй аккаунт в системе заводить не нужно
и удалённые учётные данные `QuadYellow` возвращать не придётся.

### Чем авторизуется push

На машине лежали учётные данные сразу нескольких аккаунтов, и push уходил под
первый попавшийся: `Permission to yellow444/epgu.git denied to QuadYellow`,
403. Учётные данные `QuadYellow` удалены и из `~/.git-credentials`, и из
диспетчера учётных данных Windows.

Чтобы выбор аккаунта не зависел от порядка записей, GitHub переведён на
credential helper от `gh`:

```
credential.https://github.com.helper = !gh auth git-credential
```

`gh` авторизован под `yellow444` (активный) и под рабочим аккаунтом. Push идёт
от активного, поэтому после `gh auth switch` он поедет под другим аккаунтом.
Остальные хосты остались на прежнем helper, их это не задело.

Отдельно стоит знать: `~/.git-credentials` хранит токены открытым текстом, там
лежат ключи и от других хостов. Файл на совести машины, не проекта, но при
случае его стоит перевести на менеджер учётных данных.

## Авторы

В истории должно оставаться ровно два участника:

```
Maksim <yellow444@gmail.com>
Maksim Shatov <maksim@shatov.info>   (introquest)
```

Подпись со второго, рабочего аккаунта из истории убрана: это тот же человек, но
GitHub показывал его отдельным контрибьютором. Проверка по всем веткам, включая
серверные: коммитов с прежними подписями не осталось, `git log --remotes` даёт
ровно эти два адреса.

В [`.mailmap`](../../.mailmap) остались только эти две каноничные подписи.
Сопоставления с прежними подписями оттуда убраны: коммитов с ними нет, а
корпоративный адрес такая строка публиковала открытым текстом. Строка без
прежней формы всё так же приводит имя к каноничному виду для любого коммита с
этим адресом, `git shortlog -sne --all` показывает двух участников.

Важно: GitHub привязывает коммит к аккаунту строго по email автора. Поэтому
переименование без смены email ничего не меняет, а смена email меняет всё.

### Кэш виджета Contributors

После переписывания истории виджет в сайдбаре репозитория продолжал показывать
трёх участников, тогда как REST API
(`GET https://api.github.com/repos/yellow444/epgu/contributors?anon=1`) и график
Insights показывали двоих. Прошло больше пяти суток, само не рассосалось.
Вывод: протух ровно один кэш, самообслуживанием не чинится, единственный путь -
обращение в GitHub Support с указанием расхождения между их же API и их же
виджетом. Обращение было подготовлено и отправлено 2026-08-05, результат в
проекте не зафиксирован.

Чего делать не стоит: удалять корпоративный email из рабочего аккаунта.
Коммитов с ним в репозитории уже нет, разрывать нечего, а если это
primary email или аккаунт состоит в организации работодателя с ограничением по
домену или SAML, удаление создаёт реальные проблемы ради строчки в сайдбаре.

## Правила по текстам и коммитам

Приняты в июне 2026 и действуют дальше:

- В коммитах и файлах репозитория нет упоминаний вспомогательных инструментов и
  их служебных каталогов.
- Тексты человеческие: дефис вместо длинного тире, `->` вместо стрелок, никаких
  эмодзи, галочек, значков и псевдографики.
- Файлы клиента (`api-gosuslugi-client/`) сохраняются в CRLF, иначе падает
  сборка CRA. Shell-скрипты - только LF, это закреплено в `.gitattributes`.
- Несвязанные правки не подбираются в коммит попутно: в рабочем дереве обычно
  лежит много незакоммиченного.
